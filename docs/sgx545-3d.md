# 3D on the PowerVR SGX545 (Intel Atom CE5310)

**Question:** can we get GLES2 out of the SGX545 on a mainline kernel, by which
route, at what cost?

**Verdict: yes — achievable. The kernel driver is written and builds clean
against 7.1.8; it has not been on hardware. Confidence high for the driver,
medium for end-to-end GLES2.**

The prevailing "Series5 SGX is a dead end" assumption is **wrong for this
part**, and wrong for a specific reason: SGX545 also shipped in Intel
Cedarview (GMA 3600/3650), and **Intel published the complete GPL
`services4`/`srvkm` kernel source for it**. It is still downloadable from the
Ubuntu archive. We do not need to reverse engineer a kernel driver, and we do
not need a shader compiler.

The folklore is true in general (nobody has ever produced a Mesa driver for
Series5) and irrelevant here, because the FOSS-Mesa path is not the path.

### 1.2 What is in it that matters

- **`services4/srvkm/hwdefs/sgx545defs.h` — 62,128 bytes of SGX545 register
  definitions.** This is the SGX545 programmer's reference that section Q5 of
  the brief wondered whether anyone had ever published. Intel published it, in
  machine-readable form, under GPL, in 2012.
- `sgxerrata.h`, `sgxfeaturedefs.h` (SGX545 feature block), `sgxmmu.h` (page
  table format), `sgxconfig.h` (heap layout).
- `services4/system/unified/sysconfig.c` (1,038 lines) — Intel's **PCI-attach**
  system-config layer: `PCIInitDev`, `OSPCISetDev`, BAR range acquisition, MSI.
  Same attach topology as our part.
- `services4/include/env/linux-intel/` — Intel environment layer.

### 1.3 Core revision — exact match

`sgxerrata.h` enumerates SGX545 revisions `100, 109, 1012, 1013, 10131,
**1014**, 10141`. Our EA-3 reports `SGX revision = 1014`.

Cedarview builds `-DSGX545 -DSUPPORT_SGX545 -DSGX_CORE_REV=10131`. Revisions
`10131` and `1014` carry the **identical** erratum set — `FIX_HW_BRN_SAMPLE_CACHE`
and nothing else. So rebuilding this tree for our silicon changes one `-D` and
produces the same workaround set as the shipped, known-working Cedarview driver.

## 2. Where the microkernel lives — Q3, answered

**The SGX545 EDM microkernel is in userspace, in `libsrv_init.so`. It is not in
the kernel module, and it is not signed.**

Measured on our own `/lib/libsrv_init.so` (DDK 1.12):

```
.text    0x2648   (9,800 bytes)   — one exported symbol: SrvInit
.rodata  0xd2f8  (54,008 bytes)   — entropy 4.53 bits/byte
```

The `.rodata` opens with the ukernel's config-key table — `MaxEDMTasks`,
`DisableClockGating`, `EDMTACodeProfile`, `USETmpRegGran`, `USETmpRegCount`,
`CacheCtrl`, `RegBoundReturnZero`, `YUVCoef00`…`YUVCoef14`,
`DisableAlphaCoefficientReOrdering` — and the tail is 8-byte-aligned USSE
machine words. "EDM" is Imagination's Event Driven Microkernel.

`/bin/pvrsrvctl` (i386, links `libsrv_init.so` + `libsrv_um.so`) is what uploads
it, via `SGXGetInfoForSrvInit` → `SGXDevInitPart2`.

Cedarview's `libsrv_init.so.1.7.862890` has a 53,640-byte `.rodata` — same size
class — and **34% of its 32-byte windows appear verbatim in ours**. Same
microkernel, two DDK builds.

**Consequence:** a reimplemented or ported kernel driver never has to contain,
sign, or synthesize firmware. It only has to accept the upload. The hard gate
the brief worried about is not a gate.

The remaining ABI constraints are real but ordinary, and all are enforced by
string-identified checks in the module:

- `UM-KM DDK Mismatch UM-(%d) KM-(%d)` — DDK version must match exactly.
- `Mismatch in SGXMKIF structure sizes` — struct layout between KM and ukernel.
- `Mismatch in driver and microkernel build options … check sgx_options.h` —
  a build-option bitmask, derived from the same `-D` flags on both sides.
- `Incompatible HW core rev (%x) and SW core rev (%x)` — with `check skipped`
  fallback paths present.

All four are satisfied by construction if you build the KM from the same DDK
tree and flag set as the UM you pair it with.

## 3. How close is Intel's 1.7 tree to what Control4 shipped?

Our `pvrsrvkm.ko` is not stripped and embeds `__FILE__` paths. It was compiled
from **43** source files. **40 of the 43 are present in the Cedarview 1.7 tree.**

Missing three:

| File | What it is | Cost |
|---|---|---|
| `refcount.c` | DDK debug refcount wrappers | none — no-op macros in release builds |
| `mutex.c` | OS mutex wrapper | trivial |
| `pvr_sync.c` | `/dev/pvr_sync`, Android explicit fences | only needed if the paired userspace uses it; 1.7 userspace does not |

Same architecture on both sides: `g_BridgeDispatchTable`, `CommonBridgeInit`,
`SetSGXDispatchTableEntry`, `BridgedDispatchKM`, `bridged_pvr_bridge.c`,
`bridged_sgx_bridge.c`. Our module's register-name strings (`EUR_CR_CORE_ID`,
`EUR_CR_CORE_REVISION`, `EUR_CR_BIF_*`, `EUR_CR_CLKGATECTL`) are exactly the
identifiers defined in `sgx545defs.h`.

Control4's driver is a stock IMG DDK tree with an `sgx_intel_ce` sysconfig
layer, as the brief hypothesised. Intel published the equivalent tree, five DDK
minor versions earlier, with the SGX545 hwdefs intact.

### Tree completeness

Of 17 locally-`#include`d headers absent from the tree, **all 17 are
unreachable in an SGX545 build**: other-core defs (`sgx520/530/531/543/554/
mpplus`) behind `#if defined(SGXnnn)`, MSVDX/VGX video-decode bridges behind
`SUPPORT_MSVDX`/`SUPPORT_VGX`, kernel-supplied `drm.h`/`drmP.h`/`pci.h`, and
PDUMP debug-driver bits. **The SGX545 build path is self-contained.**

## 4. The port is smaller than it looks — but DRM is not optional

The package is 558 files because it vendors the **whole Linux 3.2 DRM
subsystem** — Cedarview built with `-DSUPPORT_DRI_DRM` for X.Org.

**Correction to an earlier draft of this document:** I assumed we could build
with `SUPPORT_DRI_DRM` *off*, use the DDK's plain-chardev path, and drop the
vendored DRM tree entirely. That is wrong. Three things say so:

- Both candidate userspace blob sets — Control4's DDK 1.12 and Intel's
  Cedarview 1.7 — link `libdrm.so.2` and import `drmOpen`, `drmClose`,
  `drmCommandNone`, `drmCommandWrite`, `drmDropMaster`.
- Control4's `pvrsrvkm.ko` itself contains `pvr_drm.c`, `sPVRDrmIoctls` and
  `drm_ioctl` in its embedded strings.
- `/dev/dri/card0` on the stock system is that node.

So userspace reaches the driver *through DRM*, and a DRM device has to exist.

What is still true is that we do not need Cedarview's vendored Linux 3.2 DRM.
The DDK's DRM usage is tiny — `pvr_drm.c` is 479 lines and uses DRM purely as
a named device node plus five vendor ioctls. It was rewritten against mainline
DRM (`drm_dev_alloc`/`drm_dev_register`, a separately registered `pci_driver`,
ioctl numbers rebased on `DRM_COMMAND_BASE`) instead. So the port is ~43 files
plus one rewritten DRM shim, not 558.

The 3.2 → 7.1 kernel-API surface in `env/linux/` was small and enumerable, as
expected: removed macros (`__devinit`, `MODULE_SUPPORTED_DEVICE`,
`asm/system.h`, `drmP.h`), signature churn (`get_user_pages`, `access_ok`,
`class_create`, `__vmalloc`), renames (`mmap_sem`, `del_timer_sync`,
`page_cache_release`, `VM_RESERVED`), and four structural items — procfs,
timers, five-level page tables, and the page-table walk.

`CONFIG_MODULES=n` in openHC is **not** a blocker on this route — we build from
source, so it goes in-tree as `obj-y`. (It *is* an absolute blocker for the
stock `.ko`, which additionally has `vermagic=3.12.74` and depends on Intel's
`osal_linux`/`pal_linux` shims.)

Prior art for the port exists: [`thomas001/cedarview-drm`](https://github.com/thomas001/cedarview-drm)
took this same tree to Linux 3.10/3.11.

### Status: done, and it builds

The port is implemented in a separate repository, `sgx545-ce`, structured so
the upstream/ours boundary stays verifiable — the first commit is Intel's tree
imported verbatim, everything after it is ours.

```
pvrsrvkm.ko   156 KB   Linux 7.1.8 / i686   0 unresolved symbols
alias:   pci:v00008086d0000089B
depends: (none)
```

For scale, Control4's stock DDK 1.12 module is 182 KB and depends on
`osal_linux` and `pal_linux`.

## IT WORKS — GLES2 rendering confirmed on hardware, 2026-08-27

```
GL_VENDOR   : Imagination Technologies
GL_RENDERER : PowerVR SGX 545
GL_VERSION  : OpenGL ES 2.0 build 1.7@862890

  compile shaders (USSE compiler)       ok
  link program                          ok
  draw a triangle                       ok
  read back the centre pixel            rgba(0,255,0,255) -- the shader's green
  eglSwapBuffers (to the panel)         ok
```

Blue background, green triangle, visually confirmed on the panel. The USSE
shader compiler — the piece nobody has ever reimplemented — compiled and linked
a shader pair, and the GPU rasterised it.

**Four bugs stood between "the module builds" and this, none of them findable
without hardware:**

| # | bug | symptom |
|---|---|---|
| 1 | fops missing `FOP_UNSIGNED_OFFSET` | userspace could never `open()` the DRM node |
| 2 | bus id hardcoded to Cedarview's `0000:00:02.0` inside the blob | `drmOpen` returned −1, no ioctl ever issued, empty dmesg |
| 3 | DDK's core-rev exception loop bound counts pairs but indexes elements | our exception was never compared |
| 4 | fbdev PFN check assumes `remap_pfn_range` semantics | blocked every GLES surface |

Plus the insight that `SGX_CORE_REV` must follow the **microkernel**, not the
silicon, because it selects the shared `SGXMKIF` struct layout.

### How fast is it, for a UI?

Measured with `tools/gpubench.c` at 720x480:

| layers | opaque | blended | textured |
|---|---|---|---|
| 1 | 30.3 fps | 28.8 | 28.8 |
| 2 | 28.8 | 28.8 | 28.8 |
| 4 | 28.8 | 28.8 | 28.8 |
| 8 | 28.8 | 28.8 | 28.8 |

**Flat.** Eight layers of full-screen blended compositing cost exactly what one
does, so fill rate is nowhere near the limit — the GPU is massively
over-provisioned for a launcher UI. The ~29 fps ceiling is a fixed per-frame
cost, which points at the LinuxFB WSEGL blitting the whole 720x480x4 surface on
every swap. `eglSwapInterval(0)` is accepted and changes nothing, so it is not
vsync.

If 60 fps is wanted, the thing to attack is the present path — `libpvrPVR2D_FLIPWSEGL.so`
ships alongside the blit backend and may page-flip instead of copy — not the
rendering.

For comparison the CPU manages ~302 Mpix/s of memcpy-to-framebuffer, so for a
*static* 2D launcher the CPU is not hopeless either; the GPU's win is shaders,
transforms and effects coming for free.

[drm] Initialized pvrsrvkm 1.7.862890 for 0000:01:02.0 on minor 0

And the two things that could only ever be settled on silicon both came back
as predicted, read straight off BAR0 with devmem:

| register | value | meaning |
|---|---|---|
| `CORE_REVISION` @0x20 | `0x0001000E` | **1.0.14 → SGX_CORE_REV 1014** — matches the build default exactly |
| `CORE_ID` @0x1C | `0x01150000` | stable across reads → **core is clocked and alive at boot** |
| register window | **BAR0+0** | the CE5300-specific offset, reverse-engineered from Control4's binary, **confirmed** |

`need_sample_cache_workaround` auto-derived to `Y`, correct for rev 1014.

This is the whole kernel-side thesis, verified: right core, right revision,
right register window, powered at boot, driver attaches cleanly. What it is
**not** is working 3D — see below.

### First userspace contact, and the bug it found

Ran a DDK 1.7 userspace against the driver on the same board. `SrvInit()`
returned `PVRSRV_ERROR_INIT_FAILURE`, and the kernel said:

```
WARNING: drivers/gpu/drm/drm_file.c:329 at drm_open_helper+0x39
Call Trace: drm_open <- drm_stub_open <- chrdev_open <- ... openat
```

That line is:

```c
if (WARN_ON_ONCE(!(filp->f_op->fop_flags & FOP_UNSIGNED_OFFSET)))
        return -EINVAL;
```

DRM passes the mmap offset through as an unsigned token rather than a signed
file position, and `PVRMMap` keys its lookup on `vm_pgoff` — exactly that.
Since 6.12 `drm_open_helper()` requires the fops to declare it and refuses the
open otherwise, so **userspace could never obtain a file descriptor.**
`DRM_GEM_FOPS` sets the flag for GEM drivers; our fops is hand-rolled because
the driver owns no GEM objects, so it had to be set explicitly and was not.

Fixed in `sgx545-ce` at `3ce2b12`. Verified in the compiled binary rather than
assumed: `sPVRDrmFops` reads `00000000 20000000`, and with `owner` at +0 and
`fop_flags` at +4 that is `0x20` = `FOP_UNSIGNED_OFFSET (1 << 5)`.

Only findable by running it — the module builds, loads, binds and registers
`card0` perfectly well without it.

**The next gate is pre-checked.** `SGXInit` compares a build-options bitmask
between kernel and userspace. Every symbol feeding that hash, diffed against
Cedarview's release build:

```
Cedarview: PVR_SECURE_HANDLES SUPPORT_HW_RECOVERY SUPPORT_PERCONTEXT_PB SUPPORT_SGX_HWPERF
ours:      PVR_SECURE_HANDLES SUPPORT_HW_RECOVERY SUPPORT_PERCONTEXT_PB SUPPORT_SGX_HWPERF
```

Identical, so that check should pass.

### How it is wired in

`board/ea-common/packages/sgx545-ce` is a submodule; `board/external.mk` already globs
`packages/*/*.mk`, so the package is picked up with no change there. The rest
goes through the feature mechanism:

| File | Contents |
|---|---|
| `board/ea-common/features/sgx.defconfig` | `BR2_PACKAGE_SGX545_CE=y` |
| `board/ea-common/linux/sgx.fragment` | `CONFIG_DRM=y`, PAT/MTRR, DEVMEM |
| `board/ea3-v2/ohc.features` | `emmc switch **sgx**` |
| `board/Config.in` | one `source` line |

The ordering is the part worth knowing: `common.fragment` sets
`# CONFIG_DRM is not set` because serial console is the only head on these
boards, and `build.sh` appends feature fragments *after* the board file — so
`sgx.fragment` lands last and `CONFIG_DRM=y` wins. Putting the options in
`ea3-v2.fragment` instead would also work, but only by hand-placing them after
`common.fragment`.

The package installs the source into `drivers/gpu/drm/sgx545ce/`, appends
`obj-y += sgx545ce/` to `drivers/gpu/drm/Makefile`, and drops `sgxregs` at
`/opt/ohc/bin/sgxregs`.

### What it costs: 1.25 MiB of bzImage

Measured on ea3-v2, Linux 7.1.8 / i686:

| | bytes | | % of copy window |
|---|---|---|---|
| without the `sgx` feature | 5,468,672 | 5.22 MiB | 64.6% |
| with it | 6,779,392 | 6.47 MiB | **80.1%** |
| delta | **+1,310,720** | **+1.25 MiB** | |

The ceiling is CEFDK bootlinux's copy window, which reaches the stack at
`0x813000` (8.07 MiB). That leaves **1.61 MiB of headroom**. For comparison,
`video.fragment` cost ~150 KB and its comment budgeted ~2.6 MiB of headroom —
this takes half of that in one step.

Almost none of it is the driver. The build compiles **41 objects for
`sgx545ce` and 417 for DRM core**: atomic modeset, DP/MST topology, HDCP, DSC,
SCDC, EDID, bridge and panel helpers. The driver calls into none of them — it
uses `drm_dev_alloc`/`register`, `drm_open`/`release`/`poll` and `drm_ioctl`,
and that is all.

**It is not trimmable from a defconfig.** `CONFIG_DRM=y` defaults `DRM_BRIDGE`
and `DRM_PANEL` on, and those `select` `DRM_KMS_HELPER` and
`DRM_DISPLAY_HELPER`, which have no prompt. A fragment that tries to unset any
of them is silently ignored — tried it, the image came back byte-identical.
Reclaiming the space would need a kernel patch making the helper libraries
conditional on a driver actually wanting them.

So the trade is: 3D costs a fifth of the boot window, and if a later feature
needs that space, this is the first thing to weigh against it.

## 5. Ranked routes

### Route 1 — Cedarview 1.7 KM source + Cedarview 1.7 UM blobs *(recommended)*

A matched KM/UM pair, same DDK build, same GPU core, same i386 ABI, and a
WSEGL backend that targets the framebuffer we already have.

- **Requires:** port `env/linux/` to 7.1; retarget `sysconfig.c` from
  Cedarview's PCI IDs to `8086:089b` at `01:02.0`; build `-DSGX545
  -DSGX_CORE_REV=1014`, `SUPPORT_DRI_DRM=0`; a glibc path for the blobs.
- **Have:** everything except the port.
- **Build:** ~43 files' worth of API modernisation + the sysconfig retarget.
- **Effort:** **3–8 person-weeks** to first triangle; **+2–4 weeks** to stable.
  The range is wide because the sysconfig retarget is the unknown — Cedarview's
  layer reaches for a `(0,0,0)` MCH device and Poulsbo-lineage BAR indices that
  will not map 1:1 onto CE5300.
- **Biggest risk:** the ukernel in Cedarview's `libsrv_init.so` is built for
  core rev `10131`. Errata match, so it *should* run on `1014`, but "should" is
  doing work — this is the one thing that cannot be settled by reading.

### Route 2 — Cedarview 1.7 KM source + our stock CE 1.12 blobs

Fallback if Route 1's ukernel rejects our silicon. Keeps the blobs known to
work on this exact board.

- **Requires:** everything in Route 1, **plus** closing the 1.7→1.12 ABI gap —
  bridge-table deltas, `SGXMKIF` struct sizes, the `sgx_options.h` bitmask, and
  adding `pvr_sync.c` (the CE userspace uses `/dev/pvr_sync`).
- **Effort:** **+4–10 person-weeks** on top of Route 1, and it is blind work —
  the 1.12 headers are the thing we do not have.
- **Biggest risk:** the DDK version check is exact-match; you are hand-fitting
  an ABI you cannot see.

### Route 3 — Written GPL request *(run in parallel, costs days)*

`pvrsrvkm.ko` declares `license=Dual MIT/GPL` and names
`gpl-support@imgtec.com`. Control4 shipped no corresponding source and states a
GPL written offer in its
[legal notices](https://www.control4.com/help/c4/software/rn/os333/Content/OS%203.3.3/Legal%20Notices.htm)
([portal](https://docs.control4.com/o/opensource/)). A successful request yields
the **exact 1.12 tree**, which collapses Route 2 into Route 1.

- **Effort:** hours to write; weeks to months to resolve.
- **Risk:** low cost, low-to-moderate odds. Snap One/ADI inherited the
  obligation; the practical friction is that the graphics tree came from Intel's
  CE SDK, so they may route it to Intel and stall. Worth sending regardless —
  it is the only route that costs almost nothing.

### Route 4 — TI 1.17 tree as porting scaffold

[`git.ti.com/graphics/omap5-sgx-ddk-linux`](https://git.ti.com/cgit/graphics/omap5-sgx-ddk-linux/)
is the same `services4` codebase already ported to modern kernels — branches
`ti-img-sgx/1.17.4948957/{k4.14,k4.19,k5.4,k5.10,k6.1}` and
`1.14.3699939/{k4.1,k4.4,k4.9,k4.14}`. Its `env/linux/` is 13 years newer than
Cedarview's.

**But its `hwdefs/` has `sgx530defs.h`, `sgx540defs.h`, `sgx544defs.h` and no
`sgx545defs.h`** — TI never shipped a 545. So this is a *scaffold*, not a
source: take TI's modernised OS layer, graft Cedarview's SGX545 hwdefs and
Intel's PCI sysconfig.

Attractive on paper, but it means reconciling two DDK versions (1.17 vs 1.7)
*and* two userspace ABIs. **Only worth it if Route 1's port fights back harder
than expected.**

### Route 5 — Pure FOSS: Mesa Gallium + USSE compiler

**Not viable.** [`Garnet/sgx540-reversing`](https://codeberg.org/Garnet/sgx540-reversing)
is the high-water mark: a partial assembler/disassembler, shader replacement, an
ARMv7 debugger backend. Explicitly unfinished on full instruction encoding,
instruction semantics, MOE, PDS, and the microkernel; no independent rendering;
SGX540 only; last activity **October 2022**. Mainline's `powervr` DRM driver is
Rogue-only and its PCO compiler targets Rogue ISA.

Even with `sgx545defs.h` in hand — which is the register map, not the ISA — this
is **multiple person-years** and has defeated every group that has tried since
2011. The register map does not shorten it, because the missing piece is the
shader ISA and the compiler, not the MMIO layout.

### Route 6 — OpenCL instead of GL

**Worse, not better.** SGX545 does support OpenCL 1.0, and `libIMGegl.so`
`dlopen`s **`libPVROCL.so`** — so the DDK has an OpenCL module for this part.
**Neither Intel nor Control4 ever shipped that `.so`**: it is absent from our
stock rootfs and from the Cedarview package.

So OpenCL needs the same kernel driver as GL *plus* a userspace runtime nobody
distributed. The "smaller compiler surface" argument does not apply, because we
are not writing the compiler on the recommended route — we already have
`libglslcompiler.so` + `libusc.so` (1.29 MB, present on our image).

## 6. Next experiments, by information gained per hour

**1. Read the SGX ID registers on the live EA-3 — 30 minutes.**
BAR0 is `0xdc000000`. From `sgx545defs.h`:

```
EUR_CR_CORE_ID        0x001C    ID = bits 31:16, CONFIG = bits 15:0
EUR_CR_CORE_REVISION  0x0020    MAJOR 23:16, MINOR 15:8, MAINTENANCE 7:0
EUR_CR_CLKGATECTL     0x0000
EUR_CR_SOFT_RESET     0x0080
```

`sgx545-ce/tools/sgxregs.sh` does this: finds the device by PCI id, takes BAR0
from sysfs, reads and decodes those registers. Needs `CONFIG_DEVMEM=y` and
`CONFIG_STRICT_DEVMEM=n` (both in the repo's `linux.fragment`).

This independently confirms revision 1014, proves the BAR is mapped and the
block is clocked under our mainline kernel, and costs almost nothing. **Do this
first** — if the core is powered down at boot, that is a clock/power-gating
problem to solve before any driver work, and it is far cheaper to learn now
than after a day of debugging a driver that was never going to respond.

**2. ~~Compile-only build of the 1.7 tree against 7.1~~ — done.**
The full port is in the `sgx545-ce` repository: 41 objects, zero unresolved
symbols, `pvrsrvkm.ko` 156 KB. The estimate held — the API surface was small
and enumerable. The one surprise was that DRM could not be dropped (see §4).

**3. Load it — an hour, once experiment 1 says the core is alive.**
Build openHC with `BR2_PACKAGE_SGX545_CE=y`, boot, and watch for

inferred. Expect it not to work first time; the driver has never run.

**4. Capture a stock-system ground truth — half a day.**
Boot the stock 3.12.74 image on the EA-3, run `pvrsrvctl --start`, and capture

init sequence, the working build-option bitmask, and the ukernel upload size —
the reference trace to debug against. Worth doing before rather than after the
first failure.

**5. Send the GPL request — 1 hour.** Route 3. No reason to wait.

## 7. Putting a UI on it: WPE WebKit

The reason to want GLES on this box is not to run demos, it is to draw a
launcher without the Atom doing the compositing. WPE WebKit is the browser
engine designed for exactly that shape of device: no X server, no window
system of its own, renders through EGL/GLES.

### 7.1 The obstacle is packaging, not code

WPE reaches a display through a **libwpe backend**, `dlopen`'d at runtime and
chosen by `WPE_BACKEND` (falling back to `libWPEBackend-default.so.1`). The
standard backend, `wpebackend-fdo`, is built on Wayland — and the DDK's WSEGL
layer offers X11/DRI, LinuxFB, Front, Blit and Flip, but **no Wayland**; the
DDK is from 2011 and Wayland was not yet something a vendor shipped against.

The obvious reading is "WPE needs Wayland, so WPE is out". That is wrong, and
it is worth being precise about why, because the same mistake would rule out
the whole route:

- WebKit's own cmake has no such requirement — it links `libwpe`, not any
  particular backend. Confirmed empirically: with the dependency dropped
  (`build/buildroot-patches/0001-wpewebkit-do-not-require-wpebackend-fdo.patch`)
  WPE's cmake configure **completes**.
- The requirement lives entirely in Buildroot: `wpebackend-fdo` in
  `WPEWEBKIT_DEPENDENCIES`, plus `select BR2_PACKAGE_WPEBACKEND_FDO` and
  `depends on BR2_PACKAGE_HAS_LIBEGL_WAYLAND` in its `Config.in`.

So the coupling is packaging, not an architectural constraint — but it is not
the one-line deletion it first looks like, and getting it wrong is quiet:

- The `.mk` dependency and the kconfig `select` are **separate**. Dropping only
  the former still builds wayland, wayland-protocols and an unusable Wayland
  backend into the rootfs, because kconfig honours the select regardless.
- Buildroot never lists `libwpe` as a wpewebkit dependency **at all**. WebKit
  reaches it only *through* fdo, whose own `DEPENDENCIES` include it, and
  `BR2_PACKAGE_LIBWPE` is set only because fdo's `Config.in` selects it. On the
  live tree the config genuinely reads

  ```
  # BR2_PACKAGE_LIBWPE is not set
  BR2_PACKAGE_WPEBACKEND_FDO=y
  ```

  with libwpe built anyway. So deleting the fdo dependency without putting
  `libwpe` in its place removes WebKit's only ordering guarantee on a library it
  actually links — `wpe-webkit-2.0.pc` carries `Requires: … wpe-1.0`. The patch
  therefore *replaces* fdo with libwpe rather than dropping it.

### 7.2 wpebackend-pvr

Written for this board: `board/ea-common/packages/wpebackend-pvr`, ~300 lines of C
(also at `github.com/The1TrueJoe/wpebackend-pvr`). It implements the five
libwpe interfaces and exports exactly one symbol, `_wpe_loader_interface`.

The design is simpler than a Wayland backend because there is no compositor to
negotiate with:

| libwpe asks | we answer | why |
|---|---|---|
| native display | `EGL_DEFAULT_DISPLAY` | the LinuxFB WSEGL opens `/dev/fb0` itself |
| native window | `0` | there is one surface and it *is* the screen |
| frame rendered | acknowledge immediately | `eglSwapBuffers` blits to `/dev/fb0` and returns, so the pixels are already on the panel |
| offscreen window | `0` | see below — unverified |

That third row is the same fact as the 29 fps ceiling in §4: the present is a
synchronous full-surface blit. It costs us a frame rate cap and buys us a
backend with no frame callbacks, no buffer pool and no round trip.

**Unverified:** the offscreen target returns no native window, which asks
WebKit to make its sharing context surfaceless or pbuffer-backed. DDK 1.7
predates `EGL_KHR_surfaceless_context`. If WebKit reports it cannot create the
sharing context, check `eglQueryString(dpy, EGL_EXTENSIONS)` first; the EGL 1.4
fallback is a 1x1 pbuffer.

### 7.3 A bug that only shows up downstream: the DDK's egl.pc

The DDK installs a `pkg-config` file written for its X11/DRI window system:

```
Requires.private: libdrm >= 2.4.25 dri2proto >= 2.4 glproto >= 1.4.13 \
                  x11 xext xdamage xfixes xxf86vm
```

None of those exist here. `Requires.private` looks like it should be harmless
for a shared build — it exists for static linking — but pkgconf resolves it
even for a plain `--cflags` and **errors when it cannot**. So the damage is not
confined to things that want EGL: cairo
built with cairo-gl records `Requires: egl` in its own `cairo.pc`, and from
that point every `pkg-config cairo` in the tree errors with

```
Package 'x11', required by 'egl', not found
```

This is what stopped harfbuzz finding a cairo that had demonstrably compiled
minutes earlier — a failure whose message names X11, three packages away from
the package that actually broke. `sgx545-um` now strips the `Requires:` lines;
in the fbdev configuration the DDK libraries link nothing outside the DDK, so
the list was not merely unsatisfiable, it was wrong.

### 7.4 What still had to be written

**A surface.** Buildroot builds WebKit with `ENABLE_MINIBROWSER=OFF`, so
nothing in the image creates a view. `board/ea-common/packages/ohc-webview` is ~120 lines: make
one `WebKitWebView`, load a URL, run a main loop. No chrome, no navigation, no
tabs. The URL comes from `argv[1]` or `$OHC_WEBVIEW_URL`; what serves it is not
openHC's concern.

**The bus-id shim, system-wide.** `libsrv_um` calls
`drmOpen(NULL, "pci:0000:00:02.0")` — the Cedarview address, not ours. Because
the *name* argument is NULL, libdrm has no name-based fallback to reach: the
open just fails, with no ioctl issued and nothing in dmesg. So EGL does not
initialise at all, and a GLES program without the shim is not degraded, it is
broken. It is therefore installed in `/etc/ld.so.preload` rather than left to
each caller — WPE in particular does its rendering in a separate WebProcess,
and that is the process that needs it.

### 7.5 Status

Kernel driver, userspace blobs and GLES2 are verified on hardware (§4).

The WPE half has **not** been run on the board yet, but it is further along
than "written". `wpebackend-pvr` compiles clean (`-Wall -Wextra`, no warnings)
against the real libwpe 1.16.0 and DDK EGL headers taken out of the build's own
staging tree, and every entry point in all five libwpe interfaces is
implemented — the only NULL members are libwpe's `_wpe_reservedN` ABI padding,
which are supposed to be NULL. So the interface shape is confirmed against the
actual library rather than assumed.

Two things that check settled, worth recording because both would otherwise
have cost a build cycle:

- WebKit 2.44 installs **`wpe-webkit-2.0.pc`** and no `wpe-webkit-1.1.pc`. The
  API `ohc-webview` uses is unchanged across the rename —
  `webkit_web_view_backend_new(struct wpe_view_backend *, GDestroyNotify,
  gpointer)` and `webkit_web_view_new(WebKitWebViewBackend *)` both still exist.
- The DDK's `eglplatform.h` puts its `MESA_EGL_NO_X11_HEADERS` branch *inside*
  `#elif defined(__unix__)`. That is invisible on Linux and fatal anywhere
  else, so a host-side syntax check of anything including `<EGL/egl.h>` needs
  `-D__unix__` or it dies on `#error "Platform not recognized"` — a failure
  that looks like a broken header and is not. The open questions are the surfaceless context above, input event
plumbing (the view backend has the dispatch entry points but nothing feeds
them), and whether the ~29 fps present ceiling is acceptable for a launcher or
forces a move to `libpvrPVR2D_FLIPWSEGL.so`.

### 7.6 The constraint that actually decides this: RAM

Measured on the live EA-3 (2026-08-28), before running WPE on it:

```
MemTotal:  190720 kB
```

**186 MB.** That is very likely below what WPE needs: the engine's own shared
object is tens of megabytes before a page is loaded, and WebKit is
multi-process — a UIProcess and a WebProcess, each with its own heap — so
published guidance for WPE on embedded targets lands in the low hundreds of MB
for a real page.

To be precise about what is and is not established: **this has not been
measured on this board.** WPE has never been run here. 186 MB may well be
enough for a deliberately simple page, and the first test should just be to try
it, because the alternative carries real risk (below). What is established is
that the headroom is not there for a normal dashboard, and that the ceiling is
artificial.

Worth noticing that none of this has anything to do with the GPU. It would have
killed the route for an unrelated reason.

Except the memory is there. CEFDK's e820 map:

```
[mem 0x00100000-0x0c7fffff]  System RAM        <- 200 MB
[mem 0x0c800000-0x7fffffff]  device reserved   <- 1.8 GB
```

The board has 2 GB fitted. Linux is given the first 200 MB and the rest is
carved out for the Intel CE media stack — decode buffers, demux, display
planes — which openHC does not load. The reference design for this SoC is a
set-top box; a controller running a launcher is not one, so the entire
partition is dead weight.

**Evidence it is real, idle memory and not merely address space:**

| check | result |
|---|---|
| `/proc/iomem` claims inside the 1.8 GB | exactly one: `ce5300-fb` at `0x7fc00000` |
| does DRAM exist at the top of the range? | yes — simplefb draws through `0x7fc00000` and the panel shows it |
| write test at `0x40000000` (1 GB) | `0xa5a5a5a5` and `0x5a5a5a5a` both read back; original restored |
| aliasing into low memory? | no — neighbour word undisturbed, and low addresses read entirely different values |
| has anything written it since boot? | no — much of it still holds CEFDK's address-walking test pattern (`0x30000000` reads `0x30000000`) |

`memmap=nn@ss` forces a range back to `E820_TYPE_RAM`, additively — without
`exactmap` the rest of the map is untouched. `memmap=1024M@0x10000000` takes
1 GB starting at 256 MB and stops well short of the framebuffer, which would
put the box at ~1.2 GB and make WebKit comfortable rather than impossible.

**Sequencing.** Run WPE at 186 MB first and see what actually happens — an OOM
kill is cheap and informative, and it costs nothing but a reboot. Reclaim only
if that fails, because reclaiming is the step that can strand the board.

**Not enabled.** It belongs in `board/ea3-v2/linux/ea3-v2.fragment`, where it
is written out and commented, and it should be switched on with a serial
console attached: if any of the reclaimed range is live after all, the kernel
does not warn, it corrupts and panics, and this board's only recovery path is
the factory-restore button and the CEFDK shell. Widen in stages.

It is also specific to the EA-3 v2 measured here. The EA-1 boards have not been
measured, and a `memmap=` past the end of real DRAM is not recoverable
remotely.

### 7.7 The other ceiling: 720x480, and why

The panel is 720x480 and that is not a setting anywhere in openHC. CEFDK leaves
the VDC display pipe enabled with a 720x480 timing and the `upp_c` plane
scanning ARGB8888 out of `0x7fc00000`; all `ce5300-fb` does is hand that
existing buffer to `simple-framebuffer`. simplefb has no modeset path by
design — it describes a framebuffer somebody else configured.

So the launcher UI is SD until someone drives the VDC properly, which means a
real modeset driver against the register map in the vendor's `gdl_server.ko`
(`board/ea-common/drivers/video/fbdev/ce5300-fb.c` documents the four registers
already recovered). That is a separate project from 3D and is not required for
any of the above.

Two consequences worth holding together:

- It softens the 29 fps result. A 720x480x4 surface is 1.38 MB, and the WSEGL
  blits all of it per swap; the same code at 1280x720 would move 3.5x as much.
  Whatever replaces the blit matters more, not less, at a higher resolution.
- It constrains the RAM reclaim. The framebuffer lives at `0x7fc00000`, inside
  the reserved window §7.6 wants to hand back to Linux, and `ce5300-fb`
  explicitly refuses to probe if `page_is_ram()` says its buffer became System
  RAM. A `memmap=` that reaches it costs the display. `1024M@0x10000000` ends
  at `0x50000000` and is well clear.

### 7.8 One decision this configuration has already made: no audio in the browser

The `audio` feature gives the box ALSA, shairport-sync and librespot. None of
that reaches WPE. Buildroot enables WebKit's media stack only when gstreamer1
is selected:

```
ifeq ($(BR2_PACKAGE_GSTREAMER1),y)
WPEWEBKIT_CONF_OPTS += -DENABLE_VIDEO=ON -DENABLE_WEB_AUDIO=ON ...
```

gstreamer is not selected, so WPE is built `ENABLE_VIDEO=OFF`,
`ENABLE_WEB_AUDIO=OFF`, `ENABLE_MEDIA_STREAM=OFF`. A page can drive the
speakers only by asking something outside the browser to do it.

That is the right default here — a launcher does not stream, the engine is
smaller and lighter without it, and this hardware has 186 MB (§7.6). But it is
a **cmake-time** choice, not a runtime one: turning it on later changes global
compiler defines and rebuilds WebKit from scratch, which is many hours. Worth
deciding deliberately rather than discovering when a page stays silent.

### 7.9 Bring-up runbook

Nothing below has been run yet. It is written down so the first attempt tests
one thing at a time instead of discovering three failures at once.

**Flash.** `output/images` after a successful build:

```
ohc-flash discover
ohc-flash install <host> --images output/images --yes
```

**Check the pieces arrived** before running anything:

```
ls -l /usr/lib/libWPEBackend-pvr.so.1 /usr/lib/libWPEBackend-default.so.1
cat /etc/ld.so.preload            # -> /usr/lib/sgx-busidshim.so
pkg-config --cflags egl           # must NOT mention x11
ls /usr/libexec/wpe-webkit-*/     # WPEWebProcess, WPENetworkProcess
```

The `default` symlink is what makes this work without `WPE_BACKEND` set; the
preload is what makes EGL initialise at all (§7.4).

**Run it.**

```
ohc-webview http://localhost/
```

That URL is the default, and it is **ohc-webd** — but note that
`board/common/rootfs-overlay/opt/ohc/bin/` is gitignored, so on a fresh clone
it is empty and no dashboard ships. `make webd` stages it. If the page fails to
load with `Connection refused`, check that before suspecting WPE:

```
ls /opt/ohc/bin/ohc-webd && wget -qO- http://localhost/ | head -c 200
```

No need to stop the splash first. `ohc-splash` draws once and exits — it is not
a daemon, which is why `S01splash stop` is deliberately a no-op — so nothing
holds `/dev/fb0` and WPE simply draws over what is there. If the screen still
shows the banner after WPE claims to have rendered, that is a real symptom
(see the blank/black row below), not the splash winning a fight.

**Expected failure modes, in the order they are likely, and what each means:**

| symptom | reading |
|---|---|
| `no libwpe backend` | the default symlink is missing — packaging, not code |
| EGL fails to initialise, nothing in dmesg | the preload did not take; check `/etc/ld.so.preload` and that `drmOpen` is being intercepted |
| cannot create sharing context | the offscreen question in §7.2 — check `eglQueryString(dpy, EGL_EXTENSIONS)` for `EGL_KHR_surfaceless_context`, fall back to a 1x1 pbuffer |
| OOM kill | §7.6 — the 186 MB ceiling. Try a trivial page first; reclaim only if that also dies |
| renders, but blank/black | try `OHC_WEBVIEW_NOACCEL=1`. If it draws with that and not without, the fault is in the EGL path, not the page |
| draws, but nothing responds | expected — there is no input plumbing yet. The view backend has the dispatch entry points; nothing feeds them |

That last row is the honest state of it: rendering and input are separate
problems, and only the first is attempted so far.
